# zip 내부 검사 설계

## 목적

다운로드된 zip 파일 내부의 Word, Excel, PDF, 기타 파일들이 정해진 규칙대로 작성되었는지 검사한다.

## 실제 다운로드 형태

다운로드 시 zip 1개가 생성되는 것이 아니라 개별 파일들이 각각 다운로드된다.

따라서 '다운로드 확인' 단계(9단계)에서는 zip 손상 여부가 아니라 폴더 내 파일 존재/개수/크기를 확인한다.

검사 규칙(11단계)에서는 개별 파일(Word, Excel, PDF 등)을 직접 검사한다.

## 검사 결과 최소 단위

결과는 아래 단위까지 조회할 수 있어야 한다.

```text
작업
→ 프로젝트
→ zip 파일
→ 내부 파일
→ 검사 규칙
→ 검사 결과
```

## 규칙 저장 방식

규칙은 자주 바뀌지는 않지만 변경 가능성이 있으므로 DB에 저장하고, 상세 조건은 JSON으로 둔다.

예:

```json
{
  "sheet": "Sheet1",
  "cell": "B2",
  "expected_from": "ecm.프로젝트번호"
}
```

Word 표 검사 예:

```json
{
  "table_index": 0,
  "row": 2,
  "col": 1,
  "expected_from": "ecm.회사명"
}
```

파일명 검사 예:

```json
{
  "filename_contains": "ecm.프로젝트번호"
}
```

## 검사 유형 초안

- zip 파일명에 프로젝트번호 포함 여부
- zip 내부 파일명에 프로젝트번호 포함 여부
- Word 문서의 특정 표 위치 값 확인
- Excel 문서의 특정 셀 값 확인
- PDF 존재 여부 확인
- 특정 확장자 파일 존재 여부 확인
- 파일 저장시간 또는 수정시간 확인
- 필수 파일 누락 확인

## 실패 처리

검사 실패는 프로젝트 처리 실패와 구분한다.

- 다운로드 실패: 프로젝트 처리 실패
- zip 손상: 프로젝트 처리 실패
- 규칙 불일치: 검사 결과 실패
- 필수 파일 누락: 검사 결과 실패

## 추가로 정할 항목

- 규칙별 심각도
- 실패/경고/정보 상태 구분
- 검사 결과 화면에서 보여줄 메시지 형식
- 규칙 변경 시 버전 관리 방식

## 현재 권장 저장 방식

점검 결과는 프로젝트 최종 결과와 규칙별 상세 결과를 분리한다.

- 프로젝트 최종 결과: `DownloadReviewProject.review_status`
- 규칙별 상세 결과: `DownloadReviewRuleResult`
- 사용자 표시용 파일 정보: 규칙 결과의 `file_name`, `file_path`, `message`, `expected`, `actual`
- 관리자 확인용 원문 상세: `raw_detail_json` 또는 `DownloadReviewLog`
- 저장 범위: 작업에 포함되어 실제 점검한 프로젝트마다 규칙 개수만큼 저장한다.
- 저장 대상: 통과한 규칙과 실패한 규칙을 모두 저장한다.

판정 기준:

- 모든 규칙 통과: `review_status=completed`, `ecmlist.db` 점검결과 `O`
- 하나라도 부적합: `review_status=needs_fix`, `ecmlist.db` 점검결과 `X`
- `ecmlist.db`의 산출물별 점검 컬럼은 실제 점검규칙과 1:1로 대응하므로 해당 컬럼에 최신 `O/X`를 기록한다.
- 미실행/대상 없음 기본값은 빈 값으로 둔다.
- 다운로드/agent/분석 실행 실패: workflow DB에서는 실패/보류로 표시한다. `ecmlist.db` 점검결과와 산출물별 컬럼에는 규칙 판정 `O/X`만 기록한다.

사용자 화면에는 서버 절대경로를 표시하지 않는다. 프로젝트 폴더 기준 상대 경로 또는 파일명만 표시한다.

## 분석 완료 후 파일 정리

다운로드 파일과 폴더는 규칙 분석 완료 후 삭제한다.

삭제 전에 DB에 남겨야 하는 정보:

- 다운로드된 파일명
- 파일 크기
- 규칙별 판정 결과
- 사용자용 메시지
- 관리자 로그 event code

`ecmlist.db`는 삭제하지 않는다. 프로젝트별 점검결과와 산출물 컬럼만 추가/수정한다.
