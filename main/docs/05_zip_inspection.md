# zip 내부 검사 설계

## 목적

다운로드된 zip 파일 내부의 Word, Excel, PDF, 기타 파일들이 정해진 규칙대로 작성되었는지 검사한다.

## 실제 다운로드 형태

다운로드 시 zip 1개가 생성되는 것이 아니라 개별 파일들이 각각 다운로드된다.

따라서 '다운로드 확인' 단계(9단계)에서는 zip 손상 여부가 아니라 폴더 내 파일 존재/개수/크기를 확인한다.

검사 규칙(11단계)에서는 개별 파일(Word, Excel, PDF 등)을 직접 검사한다.

## 검사 결과 최소 단위

결과는 아래 단위까지 조회할 수 있어야 한다.

```text
작업
→ 프로젝트
→ zip 파일
→ 내부 파일
→ 검사 규칙
→ 검사 결과
```

## 규칙 저장 방식

규칙은 자주 바뀌지는 않지만 변경 가능성이 있으므로 DB에 저장하고, 상세 조건은 JSON으로 둔다.

예:

```json
{
  "sheet": "Sheet1",
  "cell": "B2",
  "expected_from": "ecm.프로젝트번호"
}
```

Word 표 검사 예:

```json
{
  "table_index": 0,
  "row": 2,
  "col": 1,
  "expected_from": "ecm.회사명"
}
```

파일명 검사 예:

```json
{
  "filename_contains": "ecm.프로젝트번호"
}
```

## 검사 유형 초안

- zip 파일명에 프로젝트번호 포함 여부
- zip 내부 파일명에 프로젝트번호 포함 여부
- Word 문서의 특정 표 위치 값 확인
- Excel 문서의 특정 셀 값 확인
- PDF 존재 여부 확인
- 특정 확장자 파일 존재 여부 확인
- 파일 저장시간 또는 수정시간 확인
- 필수 파일 누락 확인

## 실패 처리

검사 실패는 프로젝트 처리 실패와 구분한다.

- 다운로드 실패: 프로젝트 처리 실패
- zip 손상: 프로젝트 처리 실패
- 규칙 불일치: 검사 결과 실패
- 필수 파일 누락: 검사 결과 실패

## 추가로 정할 항목

- 규칙별 심각도
- 실패/경고/정보 상태 구분
- 검사 결과 화면에서 보여줄 메시지 형식
- 규칙 변경 시 버전 관리 방식

## 현재 권장 저장 방식

점검 결과는 프로젝트 최종 결과와 규칙별 상세 결과를 분리한다.

- 프로젝트 최종 결과: `DownloadReviewProject.review_status`
- 규칙별 상세 결과: `DownloadReviewRuleResult`
- 사용자 표시용 파일 정보: 규칙 결과의 `file_name`, `file_path`, `message`, `expected`, `actual`
- 관리자 확인용 원문 상세: `raw_detail_json` 또는 `DownloadReviewLog`
- 저장 범위: 작업에 포함되어 실제 점검한 프로젝트마다 규칙 개수만큼 저장한다.
- 저장 대상: 통과한 규칙과 실패한 규칙을 모두 저장한다.

판정 기준:

- 모든 규칙 통과: `review_status=completed`, `ecmlist.db` 점검결과 `O`
- 하나라도 부적합: `review_status=needs_fix`, `ecmlist.db` 점검결과 `X`
- `ecmlist.db`의 산출물별 점검 컬럼은 실제 점검규칙과 1:1로 대응하므로 해당 컬럼에 최신 `O/X`를 기록한다.
- 미실행/대상 없음 기본값은 빈 값으로 둔다.
- 다운로드/agent/분석 실행 실패: workflow DB에서는 실패/보류로 표시한다. `ecmlist.db` 점검결과와 산출물별 컬럼에는 규칙 판정 `O/X`만 기록한다.

사용자 화면에는 서버 절대경로를 표시하지 않는다. 프로젝트 폴더 기준 상대 경로 또는 파일명만 표시한다.

## 분석 완료 후 파일 정리

다운로드 파일과 폴더는 규칙 분석 완료 후 삭제한다.

삭제 전에 DB에 남겨야 하는 정보:

- 다운로드된 파일명
- 파일 크기
- 규칙별 판정 결과
- 사용자용 메시지
- 관리자 로그 event code

`ecmlist.db`는 삭제하지 않는다. 프로젝트별 점검결과와 산출물 컬럼만 추가/수정한다.

## 실제 규칙 정의 초안

### 공통 기준

- 파일명 조건은 단어 순서와 관계없이 필요한 단어가 모두 포함되는지만 검사한다.
- 폴더 탐색은 다운로드된 프로젝트 폴더 전체를 재귀 탐색한다.
- 폴더 탐색 조건을 만족하는 폴더는 1개뿐이라는 전제로, 탐색 중 첫 매칭 폴더를 찾으면 해당 폴더에서 진행한다.
- `계약` 포함 폴더, `시험` 포함 폴더 하위의 `계획` 포함 폴더처럼 폴더 조건이 있는 경우 해당 폴더 안에서만 대상 파일을 찾는다.
- 문자열 비교는 규칙별로 따로 명시하지 않으면 공백 제거 또는 정규화 없이 완전 일치를 기본으로 한다.
- 사용자에게는 서버 절대경로를 표시하지 않고 파일명 또는 프로젝트 폴더 기준 상대경로만 표시한다.

### 변수 매핑

| 변수 | 출처 |
| --- | --- |
| `{프로젝트번호}` | `ecm_list.프로젝트번호` |
| `{제품명}` | `ecm_list.제품명` |
| `{PL}` | `ecm_list.시험PL` |
| `{WD}` | `ecm_list.WD` |

`{버전}`은 별도 DB 컬럼을 두지 않고, 시험계획서 규칙에서 `{제품명}` 값 중 `ver`, `Ver`, `v`, `V`로 시작하는 부분부터 마지막까지 추출한다.

### 1. 계약서

- 산출물 컬럼: `계약서`
- 대상 폴더: `계약` 단어가 포함된 폴더
- 파일명 조건: `계약서`, `{프로젝트번호}`가 모두 포함된 파일
- 확장자 조건: `.pdf`
- 통과 조건: 대상 파일이 1개 존재한다.
- 실패 조건: 대상 파일이 없으면 파일이 없다고 통보한다.

### 2. 합의서

- 산출물 컬럼: `합의서(PDF)`
- 대상 폴더: `계약` 단어가 포함된 폴더
- 파일명 조건: `합의서`, `{프로젝트번호}`가 모두 포함된 파일
- 확장자 조건: `.docx` 1개, `.pdf` 1개
- 통과 조건:
  - `.docx`, `.pdf` 파일이 정확히 1개씩 총 2개 존재한다.
  - `.docx`, `.pdf` 파일 내 1페이지에서 `시험신청번호` 표 오른쪽 칸 값이 `{프로젝트번호}`와 일치한다.
- 실패 조건:
  - 필요한 파일이 없으면 존재하지 않는 파일을 통보한다.
  - 프로젝트 번호가 일치하지 않으면 프로젝트 번호가 맞지 않다고 통보한다.
- 증거 저장: `.pdf` 1페이지 이미지를 점검 로그에 저장하고 웹페이지에서 조회할 수 있게 한다.
- PDF 텍스트 파싱 실패 시 OCR을 시도할 수 있다.

### 3. 수수료산정표

- 산출물 컬럼: `수수료산정표`
- 대상 폴더: `계약` 단어가 포함된 폴더
- 파일명 조건: `수수료산정표`, `{프로젝트번호}`가 모두 포함된 파일
- 확장자 조건: `.xlsx`
- 통과 조건: 대상 파일이 1개 존재한다.
- 실패 조건: 대상 파일이 없으면 파일이 없다고 통보한다.

### 4. 시험환경구성도

- 산출물 컬럼: `시험환경구성도`
- 대상 폴더: `시험` 단어가 포함된 폴더의 하위에서 `계획` 단어가 포함된 폴더
- 파일명 조건: `구성도`, `{프로젝트번호}`가 모두 포함된 파일
- 확장자 조건: 없음
- 통과 조건: 대상 파일이 1개 존재한다.
- 실패 조건:
  - 대상 파일이 없으면 파일이 없다고 통보한다.
  - 대상 파일이 2개 이상이면 `시험환경구성도 파일이 여러개 존재함`이라고 통보한다.

### 5. 품질특성별제품정보기재사항

- 산출물 컬럼: `품질특성별제품정보기재사항`
- 대상 폴더: `시험` 단어가 포함된 폴더의 하위에서 `계획` 단어가 포함된 폴더
- 파일명 조건: `품질특성별`, `{프로젝트번호}`가 모두 포함된 파일
- 확장자 조건: `.docx`
- 통과 조건:
  - 대상 파일이 1개 존재한다.
  - 파일 내에 공백 정규화 후 `({프로젝트번호} 품질특성별 시험대상제품 정보 기재사항)` 문장이 존재한다.
  - 해당 문장의 바로 다음 줄에 일반적인 날짜 형식의 값이 작성되어 있다.
- 실패 메시지:
  - 파일명 조건 불일치 또는 대상 파일 없음: `파일명이 잘못되었습니다.`
  - 문장 검사 실패: `1페이지 제목이 잘못되었습니다.`
  - 날짜 검사 실패: `1페이지 날짜가 잘못되었습니다.`
- 날짜 형식은 `YYYY-MM-DD`, `YYYY.MM.DD`, `YYYY/MM/DD`, `YYYY년 M월 D일`, `MM/DD`, `M월 D일` 등 일반적으로 쓰는 날짜 표기를 폭넓게 허용한다.

### 6. 기능리스트

- 산출물 컬럼: `기능리스트`
- 대상 폴더: `시험` 단어가 포함된 폴더의 하위에서 `계획` 단어가 포함된 폴더
- 파일명 조건: `기능`, `{프로젝트번호}`가 모두 포함된 파일
- 확장자 조건: `.xls` 또는 `.xlsx`
- 통과 조건:
  - 대상 파일이 1개 존재한다.
  - 전체 시트 기준으로 시트가 1개만 존재한다.
  - 파일 내 아무 셀에 `{프로젝트번호} 기능리스트` 문장이 존재한다.
  - `작성자`가 작성된 같은 셀에 `{PL}`도 함께 작성되어 있다. 이때 공백 제거 후 비교한다.
- 실패 조건:
  - 대상 파일이 없으면 파일이 없다고 통보한다.
  - 시트가 2개 이상이면 `불필요한 시트가 존재함`이라고 통보한다.
  - 프로젝트번호 문장 또는 작성자 검사가 실패하면 `시험번호 또는 작성자가 잘못 작성됨`이라고 통보한다.
- `.xls` 처리가 필요하면 `xlrd` 등 별도 Excel reader 의존성을 추가할 수 있다.

### 7. 시험계획서

- 산출물 컬럼: `시험계획서(PDF)`
- 대상 폴더: `시험` 단어가 포함된 폴더의 하위에서 `계획` 단어가 포함된 폴더
- 파일명 조건: `계획서`, `{프로젝트번호}`가 모두 포함된 파일
- 확장자 조건: `.docx` 1개, `.pdf` 1개
- 통과 조건:
  - `.docx`, `.pdf` 파일이 정확히 1개씩 총 2개 존재한다.
  - `.docx` 파일의 2번째 표에서 아래 라벨의 오른쪽 같은 행 다음 셀 값이 기대값과 일치한다.
    - `소프트웨어 명`: `{제품명}`에서 버전 문자열을 제외한 값과 공백 제거 후 완전 일치
    - `버전`: `{제품명}`에서 `ver`, `Ver`, `v`, `V`로 시작하는 부분부터 마지막까지 추출한 값과 완전 일치
    - `시험신청번호`: `{프로젝트번호}`와 완전 일치
  - `.docx` 파일 내 `2.2 시험일정` 다음 표에서 2번째 열의 숫자가 위에서부터 `1`, `1`, `{WD}-3`, `1`과 일치한다.
- 실패 조건:
  - 필요한 파일이 없으면 존재하지 않는 파일을 통보한다.
  - `.docx`의 2번째 표 제품정보가 일치하지 않으면 `제품정보가 틀림`이라고 통보한다.
  - 시험일정 표 값이 일치하지 않으면 `시험일정 WD가 틀렸음`이라고 통보한다.
- 보류 항목:
  - `.docx` 파일 내 `<세부사양>` 다음 표와 13번 시험결과서 점검 대상 파일의 `<세부사양>` 다음 표 비교는 13번 규칙 정의 후 다시 확정한다.
  - 현재 기준으로는 LLM 없이 정규화된 셀 값 비교로 처리할 수 있다.
- 증거 저장: `.pdf` 1페이지 이미지를 점검 로그에 저장하고 웹페이지에서 조회할 수 있게 한다.

## LLM 규칙 후보

파일 존재, 확장자, 파일명 포함 여부처럼 명확한 규칙은 프로그램 규칙으로 처리한다.

문서 본문을 읽고 의미를 판단해야 하는 규칙은 LLM 규칙 후보가 될 수 있다.
다만 현재는 실제 API 호출을 연결하지 않고, 아래 인터페이스만 먼저 구현했다.

- provider-neutral payload 생성
- Claude/GPT/Gemini/내부 GPU API로 변환 가능한 `messages` 구조
- 응답 JSON schema
- 응답 파서
- 수동 테스트용 `build_llm_review_prompt` 관리 명령

관련 문서:

- `17_llm_review_interface.md`

운영 연결 전까지 LLM 결과는 자동 write-back 대상이 아니다.
특히 `warning`은 `O/X`로 쓰지 않고 사용자 확인이 필요한 상태로 다루는 것이 안전하다.
