# KOLAS 점검 페이지 (`/kolas/`)

ECM 점검 페이지(`/download-review/`)와 같은 화면·점검 엔진을 쓰되, **프로젝트 목록만 별도 테이블**로 관리하는 페이지다. `/KOLAS` 는 `/kolas/` 로 리다이렉트된다. 운영 주소는 `https://gsai.tta.or.kr/kolas/` — IP 주소(`210.96.71.194`)로 접속하면 도메인으로 308 리다이렉트되므로 IP로는 쓸 수 없다.

## 구조 한눈에

| 항목 | 내용 |
| --- | --- |
| 화면 | `review/ecm_download_review.html` / `ecm_download_review.js` 재사용. 뷰가 `kolas_mode` 를 넘기면 제목·미배정 탭·`결과서 다운로드` 버튼이 켜지고, JS 는 `downloadReviewPageConfig` 로 KOLAS 모드를 안다 |
| 프로젝트 목록 | `kolas_project`(reference DB, 모델 `KolasProject`). 기존 `reference_project` 와 완전히 분리 — 기존 ECM 점검 페이지 목록에는 나타나지 않는다 |
| 목록 API | `/kolas/api/projects/`, `/kolas/api/pl-assignments/`(+`apply/`) — `main/views/review/kolas_api.py` |
| 점검 작업 | 기존 `/api/jobs/` 를 그대로 사용. 생성 시 `source:"kolas"`, 목록 조회 시 `?source=kolas`. 워커·대기열은 ECM 페이지와 **공유**(단일 워커). `DownloadReviewJob.source`(workflow DB)로만 구분 |

## 대상 프로젝트

`python manage.py sync_kolas_projects` 가 구글시트 두 장(2026 `gid=740274777`, 2025 `gid=1283834444`)을 읽어 적재한다.

- 기준: **종료예정일(G열)** 이 2025-05-14 ~ 2026-09-23 (`--start/--end` 로 변경). 날짜를 못 읽은 행은 제외하고 개수·번호를 출력한다.
- 파서는 `main/utils/kolas_sheet.py`. 기존 `ecm_reference_sheet.parse_sheet_projects` 와 달리 `GS-A-25-0077` / `TTA-26-01716` 번호를 모두 읽고, `순번` 헤더 행을 찾아 데이터를 읽는다(2025년 시트·2026년 1~2월 회차는 헤더 위치가 달라 기존 파서는 통째로 건너뛴다).
- 중복 프로젝트번호: 최신 시트(2026) 우선, 같은 시트에서는 행 번호가 작은 것(=최근 회차).
- **한 셀에 프로젝트 번호가 여러 줄**(원시험 + 추가시험, 예: `GS-B-24-0127⏎GS-B-25-0136`)이면 **마지막 줄의 번호**가 그 행의 프로젝트다. 앞쪽 번호는 이전 시험 번호라 ECM 에서 같은 폴더로 찾을 수 없어 목록에 넣지 않는다. WD·신청일·계약일·시작일·종료예정일도 번호와 같은 순서로 줄이 나뉘어 있으므로 **마지막 줄 값**을 쓴다(종료예정일 필터가 마지막 프로젝트 기준). 줄 대신 공백으로 이어 붙인 날짜(`25/10/10,금 25/11/06,목`)도 마지막 날짜를 읽는다. 시험원 칸은 줄 수가 번호 수와 같을 때만 마지막 줄을 쓰고(`정은하⏎방영규`), 쉼표로 이어진 공동 시험원(`송현경, 방영규`)과 번호 수와 줄 수가 다른 회사(제품) 칸은 자르지 않는다. 번호가 하나뿐인 행은 종전과 같다.
- 번호 규칙이 바뀌면 이전에 적재된 "첫 줄 번호" 행이 DB 에 남을 수 있다. `sync_kolas_projects` 는 이번 대상에 없는데 남아 있는 행을 알려 주고(점검결과 유무 구분), `--prune` 을 붙이면 **점검결과 없는 행만** 지운다.
- 센터는 시험원(PL)으로 정한다. 웹 `PL 배정 목록`에서 한 배정(`reference_center_pl`)이 시트 기본 목록보다 우선. 어느 센터에도 없는 PL 의 프로젝트는 **미배정** 탭에 나오며 PL 배정 후에 점검 작업을 요청할 수 있다(결과서 다운로드는 미배정이어도 가능 — 전 센터 ECM 을 차례로 탐색).
- 옵션: `--dry-run`(DB 무변경), `--prune`(이번 대상에서 빠진 행 중 점검결과 없는 것 삭제), `--csv-2026/--csv-2025`(로컬 CSV).
- 동기화는 점검결과 컬럼(`review_result`, `inspection_date`, `artifact_results_json`)을 덮어쓰지 않는다.

## 점검결과 공유 규칙

기록 지점은 `ecm_reference_db._write_project_review_result_pg` 한 곳이다.

| 상황 | 동작 |
| --- | --- |
| 기존 DB(`reference_project`)에 프로젝트가 있음 | 기존 DB 를 갱신하고, KOLAS 목록에 있는 프로젝트면 같은 값을 `kolas_project` 에도 복사 |
| 기존 DB 에 없고 KOLAS 에만 있음 | KOLAS DB 에만 저장 |
| 둘 다 없음 | `ReferenceDbError` (워커는 경고 로그 후 계속) |

- ECM 점검 페이지에서 돌린 작업도 KOLAS 목록에 같은 번호가 있으면 결과가 자동으로 KOLAS 에 반영된다.
- 동기화 때(`copy_reference_results_to_kolas`) 기존 DB 에 이미 결과가 있는 프로젝트는 KOLAS 로 복사된다. 기존 DB 에 결과가 없으면 KOLAS 값을 건드리지 않는다.
- **요약(O/X, 산출물별 O/X)만 공유**된다. 규칙별 상세 결과는 `workflow.db` 의 작업 이력에서 읽으므로, 이미 점검된 프로젝트는 같은 서버(194)에서 `상세` 로 그대로 조회되고 재점검이 필요 없다. 기존 DB 에서 가져온 요약만 있고 이 서버에 작업 이력이 없는 프로젝트는 `상세` 를 눌러도 "점검 이력을 찾을 수 없습니다" 로 나온다(요약 O/X 만 보임).

## 결과서(시험성적서) 다운로드

- 선택한 프로젝트마다 센터 ECM 에서 `연도 시험서비스 → GS 1등급 → 프로젝트번호 폴더`(`find_full_project_folder`)를 찾고, `시험 > 종료` 폴더(점검규칙 8번의 `folder_keyword_chain` 과 동일)에서 파일명에 `시험성적서` 가 들어간 Word(`.doc/.docx/.docm`)·PDF 를 받는다. 못 찾으면 프로젝트 폴더 전체를 탐색한다.
- zip 구조: `word/`, `pdf/`, `_다운로드_결과.txt`(성공/누락 사유). 파일명에 프로젝트번호가 없으면 `프로젝트번호_` 를 붙이고 중복은 `(2)` 로 구분.
- zip 파일 자체는 서버 디스크에 만들지 않는다(문서 보관은 아래 "서버 저장소"). ECM 파일 하나를 메모리로 받아 검증(크기·매직바이트)한 뒤 zip 조각으로 바로 브라우저에 전송하고, 다음 파일로 넘어간다. 운영은 ASGI(Daphne)라 동기 생성기를 그대로 응답에 주면 Django 가 전부 모은 뒤 보내므로, `kolas_api._stream_body` 가 비동기 생성기로 감싸 조각마다 즉시 전송한다(nginx 버퍼링은 `X-Accel-Buffering: no` 로 끔). 한 번에 최대 `KOLAS_REPORT_MAX_PROJECTS`(기본 300)개. 프로젝트별 실패는 전체를 중단하지 않고 결과 파일에 기록한다.
- 화면은 숨은 iframe 으로 form POST 하므로 오류도 `다운로드 오류.txt` 가 든 zip 으로 내려간다.
- ECM 센터별 자격증명(`ECM_USERNAME*`)은 기존 점검 흐름과 같은 환경변수를 쓴다.

## ECM 에 zip 으로 올라간 경우 (분석·실측 단계, 아직 다운로드 로직에는 미연결)

zip 안에 시험성적서가 들어 있고 zip 이 커서 통째로 받기 어려운 경우를 위한 준비 코드다.

- 원리: zip 은 파일 끝에 목록(central directory)이 있어 임의 위치를 읽을 수 있다. `/servlet/blob` 이 HTTP Range(206)를 지원하면 끝부분 목록 + 필요한 항목만 받는다. 코드: `DestinyECM.blob_range`(`ecm_http_client.py`), `EcmRangeFile`/`open_remote_zip`(`ecm_zip_range.py`).
- Range 를 무시하고 전체(200)로 응답하면 본문을 읽지 않고 연결을 닫고 `EcmRangeUnsupported` 를 던진다(전체 다운로드 없음).
- 실서버 가능 여부는 코드로 알 수 없어 실측 명령을 둔다(결정 12b 개정: 접속 가능한 환경이면 Claude 가 직접 실행, 읽기 전용): `manage.py probe_ecm_zip --center <센터> --test-no <시험번호> [--list-only|--extract]`.
- 한국어 Windows 압축 도구는 파일명을 CP949(UTF-8 플래그 없음)로 저장하므로 `decoded_name` 이 이름을 복원한 뒤 `시험성적서` 를 찾아야 한다.
- **실측 결과(2026-10-01, 194 서버에서 읽기 전용으로 수행)**
  - `/servlet/blob` 은 Range 를 **지원하지 않는다.** POST·GET·`Mode=view`·끝부분(`bytes=-65536`) 모두 Range 를 무시하고 200(전체)으로 응답하며 `Accept-Ranges` 헤더도 없다(Apache-Coyote/1.1). HEAD 는 길이 0. → `EcmRangeFile` 방식은 쓸 수 없다.
  - ECM 웹 화면 JS(로그인 후 앱 17개 파일)에서 zip 내부 목록/미리보기 API 는 발견되지 않았다(`file/convertFileExt.do?method=requestConvertFile` 변환 요청과 `BLOBType=tn/tif` 썸네일만 있음).
  - 194 → ECM 전송 속도는 약 **41MB/s**(30MB/0.7s, 영남 서버). 124MB zip 은 약 3초, 448MB 는 약 11초 수준이라 통째로 받는 비용이 크지 않다.
  - 표본 12개 프로젝트 중 11개에 zip 이 있다. 대부분 `rawdata.zip` 등 부속 자료이고, 프로젝트 전체를 zip 하나로 올린 경우(파일 1~3개, 59~448MB)가 5건이었다. 이런 zip 은 `1.시험인증신청/…/4.시험/라.종료/…` 처럼 폴더 구조가 그대로 들어 있고 이름은 CP949(UTF-8 플래그 없음)였다.
  - 시험성적서는 zip 뒤쪽(`4.시험/라.종료`)에 있어 앞에서 찾고 중단하는 방식의 이득은 작다.
- **적용됨(2026-10-01)**: 프로젝트 폴더에 시험성적서 Word/PDF 가 직접 없을 때만 zip 안을 본다. ECM 응답을 흘려받으며 zip 로컬 헤더를 순서대로 해석해(`ecm_zip_stream.extract_matching`) 시험성적서 항목만 메모리에 모으고 나머지는 풀지도 저장하지도 않고 버린다. 전송은 zip 크기만큼 일어나지만 디스크에는 남지 않는다.
  - 열 zip 순서: 부속 자료(`rawdata`·성능·홍보·캡처·이미지·결함 등 이름)가 아닌 것 → 최상위 폴더 → 이름에 프로젝트번호 포함 → 큰 것. 부속 zip 은 다른 zip 에서 못 찾았을 때만 연다. 프로젝트당 총 전송 한도 `KOLAS_ZIP_SCAN_MAX_MB`(기본 1024MB).
  - 지원: stored/deflate, zip64, 데이터 디스크립터(deflate), CP949 이름, CRC 검증, 암호화 항목은 건너뛰고 사유 기록. 크기를 알 수 없는 stored+디스크립터 등 순차 해석이 불가능한 zip 은 임시 파일로 받아 처리하고 즉시 삭제한다(`extract_via_tempfile`).
  - 꺼낸 시험성적서는 일반 경우와 똑같이 서버 저장소에 저장돼 다음 요청부터 ECM 을 거치지 않는다. `_다운로드_결과.txt` 에는 `(ECM zip 안에서 추출)` 로 표시.
  - **실측(194 → 영남 ECM, 읽기 전용)**: `TTA-26-01271`(zip 124MB) 3.7초, `GS-C-25-0091`(zip 448MB) 9.1초에 각각 시험성적서 Word+PDF 2개를 추출. 파이썬 메모리 피크 5.7MB, 저장소에는 시험성적서 2개와 `_meta.json` 만 저장. 같은 프로젝트 재요청은 0.12초(저장본).

## 시험성적서가 업로드되지 않은 경우: 분당 ECM 익명본으로 대체

프로젝트 폴더(와 그 안의 zip)에서 시험성적서 Word/PDF 를 못 찾으면, 분당 ECM 의 **익명 시험성적서(Word)** 를 받아 결과 zip 의 `익명/` 폴더에 담는다.

- 위치: 분당 ECM 의 인증위원회 트리 `{연도} 시험서비스 > 00 {연도}년 GS인증심의위원회 > (회차) > 인증일자(yyyymmdd) > "가./나./… {시험번호}"` 폴더. **센터와 무관하게 모든 프로젝트(상암·영남 포함)의 익명본이 여기에 있다**(분당 ECM 에는 상암·영남 프로젝트 폴더가 따로 없다). 코드는 `find_committee_test_folder(시험번호, 인증위원회 개최일)` 를 쓴다. 보조로 분당 프로젝트 폴더(`4.시험/라.종료`)의 익명본도 찾는다.
- 대상 파일: 이름에 `익명` 과 `시험성적서` 가 있는 Word. 표기는 `- 익명`, `_익명`, `(익명)`, 앞쪽 `(익명) ` 등 제각각이다. `품질평가보고서 … 익명` 은 받지 않는다.
- 일반 탐색은 이름에 `익명` 이 든 파일을 원본으로 보지 않는다(분당 프로젝트 폴더에는 원본과 익명본이 함께 있어, 제외하지 않으면 `word/` 에 익명본이 섞인다).
- **서버에 저장하지 않는다.** 익명본은 고정해 둘 필요가 없으므로 요청할 때마다 본래 센터 ECM(프로젝트 폴더, zip)을 먼저 다시 찾고, 그래도 없으면 다시 분당 ECM 익명본을 받는다. 원본이 나중에 업로드되면 그 요청에서 원본이 서빙되고 **그때부터 최종본으로 저장**된다. 서버 저장소에는 각 센터 ECM 에서 찾은 최종본(`word`/`pdf`)만 있다.
- 둘 다 없으면 `_다운로드_결과.txt` 에 "원본 사유 / 익명본 대체도 실패 사유(인증위원회 트리 시도 결과 포함)" 가 기록된다. 분당 ECM 접속 실패도 같은 방식으로 기록되고 다운로드는 계속된다.
- 결과 zip: `word/`, `pdf/`, `익명/`, `_다운로드_결과.txt`. 요약에는 `분당 ECM 익명본으로 대체(…서버에 저장 안 함)` 으로 표시.
- 실측(2026-10-01, 읽기 전용): 상암 `GS-B-25-0133`, 영남 `GS-C-25-0091`·`TTA-26-01271`, 분당 `GS-A-25-0099` 모두 인증위원회 트리에서 익명 Word 1개씩(약 0.4~0.6MB)을 받아 `익명/` 에 담았고 서버 저장소는 비어 있었다(총 1.6초). 정상 경로(`GS-A-25-0099`)는 `word/`·`pdf/` 에 원본만 들어가고 익명본은 섞이지 않았다.

## 결과 로그 템플릿 (`_다운로드_결과.txt`)

결과 zip 의 맨 위 폴더에 UTF-8(BOM) 텍스트로 들어간다. 구현 `kolas_report_download.build_summary` / `row_lines`.

**원칙: 익명본을 제외하고 word·pdf 를 정상으로 받은 이력은 쓰지 않는다.** 못 찾았거나 받지 못한 것, 익명본으로 대체한 것만 쓴다. 정상으로 받은 프로젝트는 건수 요약에만 반영된다.

```text
KOLAS 시험성적서 다운로드 결과
생성 시각: YYYY-MM-DD HH:MM:SS
요청 프로젝트 N건 | word·pdf 모두 있음 a건 | 일부만 있음 b건 | 모두 없음 c건 | 익명본 대체 d건 [| 확인 불가 e건]
성공 프로젝트: x건 / 실패·누락: y건

[확인 필요 이력]                 ← 요청 순서. 문제가 없으면 "없음 (모든 프로젝트의 word·pdf 시험성적서를 정상으로 받았습니다)"
<번호> pdf 시험성적서 찾을 수 없음
...
[실패·누락]                      ← 못 찾았거나 일부 실패한 프로젝트와 사유(긴 설명)
<번호>: 사유
```

**`[확인 필요 이력]` 줄 형식**

| 상황 | 로그에 쓰이는 줄 |
|---|---|
| word 성공, pdf 없음 | `<번호> pdf 시험성적서 찾을 수 없음` (word 줄은 없음) |
| word 성공, pdf 있었으나 받기 실패 | `<번호> pdf 시험성적서 다운로드 실패 (파일명: 사유)` |
| word·pdf 모두 성공 | (아무것도 쓰지 않음) |
| word 없음, pdf 없음, 익명 word 받음 | `<번호> word 시험성적서 찾을 수 없음` / `<번호> pdf 시험성적서 찾을 수 없음` / `<번호> 익명 시험성적서(word) 다운로드 (1개, 분당 ECM 익명본으로 대체, 서버에 저장 안 함)` |
| word·pdf·익명 모두 없음 | 위 두 줄 + `<번호> 익명 시험성적서(word) 찾을 수 없음 (사유)` |
| 같은 형식의 파일이 둘 이상인데 하나만 실패 | `<번호> word 시험성적서 다운로드 실패 (파일명: 사유) - 같은 형식의 다른 파일은 받음` |
| KOLAS 목록에 없는 번호 | `<번호> word 시험성적서 확인 불가 (KOLAS 프로젝트 목록에 없음)` / pdf 도 같은 줄 |

- 건수 줄: `word·pdf 모두 있음` = 둘 다 담긴 프로젝트, `일부만 있음` = 둘 중 하나만, `모두 없음` = 둘 다 없음(익명본 대체 포함), `익명본 대체` = 익명본이 담긴 프로젝트 수(모두 없음과 겹침), `확인 불가` = KOLAS 목록에 없는 번호(다른 건수에서는 제외).
- 익명 파일은 word/pdf 유무 판단에 포함하지 않는다(원본이 있는지만 본다).
- `성공 프로젝트` = 1개 이상 담긴 프로젝트, `실패·누락` = `[실패·누락]` 절의 줄 수. 한 프로젝트에 파일 실패가 있으면 word·pdf 가 둘 다 담겼어도 `실패·누락` 에 들어갈 수 있다.

## Office 임시(잠금) 파일 제외

압축 폴더 안에는 문서를 연 채로 묶은 탓에 `~$GS-B-25-0110 시험성적서 v1.0.docx`(162바이트짜리 Office 소유자 파일), `~WRL0001.tmp`, macOS `._*`, LibreOffice `.~lock.*` 같은 임시 파일이 시험성적서와 같은 이름으로 들어 있는 경우가 많다. 이전에는 이를 Word 시험성적서로 잘못 집어 무결성 검증이 실패했고, 그 프로젝트는 `일부 파일 실패` 로 기록되면서 **서버 저장소에 저장되지 않았다**(2026-10-01 상암 291건 중 약 65건: 291건 중 저장된 폴더 212개 = 291 − 익명 대체·미발견 14 − 파일 실패 65). 지금은 이름이 `~`, `._`, `.~lock` 으로 시작하는 파일은 시험성적서로 보지 않는다(`is_temp_file_name`). 이미 요청했던 프로젝트도 다음 요청 때 정상 저장된다.

## 결과서 다운로드 진행률 (progress bar)

`결과서 다운로드` 한 번을 "작업" 하나로 기록하고, 화면의 **현재 작업 진행 상황** 탭과 **작업 조회** 탭의 `현재 단계` 칸에 0~100% progress bar 로 보여준다. 나머지 열은 모두 `-` 이다.

- 기록: 모델 `KolasReportTask`(`kolas_report_task` 테이블, **workflow DB**, 마이그레이션 `0016`). 화면이 form 으로 `task_id`(UUID)를 보내면 서버가 그 id 로 행을 만들고, zip 이 흘러가는 동안 프로젝트 단위로 갱신한다(`kolas_report_task.ReportTaskReporter`). 목록 API `GET /kolas/api/report-tasks/?limit=20`.
- 진행률은 **얼추**다: `(끝낸 프로젝트 수 + 현재 프로젝트의 단계 비율) / 전체 프로젝트 수`. 단계 비율은 저장소 확인 5% → ECM 폴더·zip 탐색 10% → 찾음 40% → 파일마다 40~95% → 프로젝트 완료 100%(익명본 조회는 55%). 정상 종료 전에는 99% 를 넘기지 않고 끝나면 100% 로 확정한다. 같은 프로젝트의 잦은 갱신은 0.4초 간격으로 줄여 DB 쓰기를 아낀다.
- 상태: `진행 중`(파랑) / `완료`(초록, 원본 word·pdf 모두/일부만/모두 없음/익명본 대체 건수 표시) / `실패`(빨강) / `취소됨`(주황, 브라우저가 다운로드를 중단). 180초 넘게 갱신이 없는 `진행 중` 작업(서버 재시작 등)은 목록 조회 때 `실패` 로 정리된다.
- 화면: 다운로드를 시작하면 1.5초 간격으로 폴링하다가 그 작업이 끝나면 멈춘다. 진행 상황 탭은 진행 중이거나 끝난 지 10분 이내인 작업만, 작업 조회 탭은 최근 20건을 보여준다. 점검 작업이 없어도 결과서 다운로드 패널은 따로 표시된다.
- 진행률 기록이 실패(DB 오류 등)해도 다운로드는 중단되지 않는다. 마이그레이션 전에는 목록 API 가 빈 목록을 돌려준다.

## 산출물 폴더 팝업 (ECM 점검 페이지·KOLAS 페이지 공용)

상세 결과 팝업의 `전체 산출물 다운로드` 버튼은 `산출물 보기`로 바뀌었다. 누르면 root 폴더(= `find_full_project_folder` 가 찾은 프로젝트 폴더)의 구조를 보여주는 팝업이 열리고, 같은 템플릿·JS 를 쓰므로 `/download-review/` 와 `/kolas/` 에 모두 적용된다. 구현 `ecm_folder_browser.py`(로직), `ecm_folder_browser_api.py`(뷰), JS `openFolderBrowser` 계열.

- **떠 있는 창**: 산출물 팝업은 모달이 아니라 떠 있는 창이다. 뒤의 점검결과 상세 팝업을 가리거나 막지 않고(바깥 막은 클릭을 통과시킨다) 따로 조작할 수 있으며, 제목줄을 끌어 옮기고 모서리로 크기를 바꾼다(위치는 다음에 열 때 기억). Esc 는 산출물 창을 먼저 닫는다.
- **탐색**: 이동 경로(breadcrumb)로 한 단계씩 들어가고 나온다. ECM 폴더는 클릭하면 들어가고, 파일은 클릭하면 그 파일만 다운로드된다. **zip 은 클릭하면 안으로 들어가고**(폴더·파일을 같은 방식으로 표시), zip 안의 zip 도 3단계까지 열린다.
- **zip 처리(임시 보관)**: ECM 은 Range 를 지원하지 않아 zip 은 처음부터 흘려받아야 한다(194→ECM 약 41~50MB/s). 서버가 zip 을 **받는 동안에는 압축을 풀지 않고 파일로만 저장**하고(`ecm_zip_cache.py`, `_spool_zip`), 다 받은 뒤 중앙 디렉터리에서 목록(이름·크기)을 한 번에 읽는다(Django cache 15분). 받는 동안 항목을 풀면 CPU 를 독점하는 스레드가 생겨 같은 서버의 다른 요청(상세 조회 등)이 GIL 을 기다리며 수 초씩 느려지는 문제가 실제로 있었기 때문이다(2026-10-02). 이후 파일 받기·폴더 zip·다중 선택·중첩 zip 은 모두 이 **서버 사본에서** 꺼내므로 ECM 을 다시 부르지 않는다. 사본이 아직 받는 중이면: 진행률 85% 이상이면 최대 120초 기다렸다 사본을 쓰고, 아니면 원래 방식(ECM 에서 흘려받아 그 항목만 보냄)으로 보낸다. 중첩 zip 은 바깥 zip 항목 데이터를 안쪽 해석기에 그대로 먹이는 파이프라인이다.
- **미리 받기**: 팝업을 열어 root 목록을 불러오는 시점에, **root 바로 아래 zip 중 가장 큰 1개**(기본 30MB 이상일 때만)를 서버가 백그라운드로 받기 시작한다. 사용자가 그 zip 을 누르면 이미 받은 만큼 활용하고 이어서 기다린다. 하위 폴더를 열 때는 미리 받지 않는다. 실패해도 root 목록에는 영향이 없다.
- **팝업을 닫으면 받던 zip 정리**: 팝업은 열 때 세션 id(`sid`)를 만들어 모든 browse 요청에 붙이고, 3초마다 `POST /api/projects/<번호>/browse/watch/`(`action=beat`)로 "보고 있다"는 신호를, 닫을 때(닫기·Esc·탭 닫기 `pagehide`) 즉시 `action=close` 를 `keepalive` 로 보낸다. 서버는 zip 마다 보고 있는 sid 목록을 두고, **보는 팝업이 하나도 없고 85% 미만**이면 받기를 그 자리에서 중단하고(다음 청크에서 연결을 닫는다) 임시 파일을 지운다. 대기열에서 아직 시작하지 않은 것은 시작하지 않는다. 다른 사용자·다른 화면(ECM 점검/KOLAS)이 같은 zip 을 보고 있으면 유지하고, 마지막 팝업이 닫히면 그때 취소한다. 85% 이상이면 끝까지 받아 둔다(보관은 정각 삭제 규칙). 닫힘 신호가 오지 못한 경우(브라우저 강제 종료·네트워크 끊김)는 beat 가 10초 끊기면 닫힌 것으로 본다(2초마다 확인). ECM 은 Range 를 지원하지 않아 중단한 받기는 이어받을 수 없고, 다시 열면 처음부터 받는다(취소가 즉시이므로 받기 자리를 오래 차지하지 않는다). `sid` 없이 들어온 요청이 만든 작업은 자동 취소하지 않는다.
- **받기 순서(우선순위 큐)**: 받기 스레드는 2개(`FOLDER_BROWSER_PREFETCH_WORKERS`)이고 대기열은 우선순위 순이다 - 사용자가 직접 연 zip(0) > 팝업을 열 때 미리 받기(1) > 다음 요청을 위한 사본 만들기(2). 대기 중인 미리 받기를 사용자가 직접 열면 대기열 앞으로 올라간다.
- **진행률**: zip 을 읽는 요청이 길어지면 팝업 안내 문구에 `N% (받은 크기 / 전체 크기)` 가 나온다(`GET /api/projects/<번호>/browse/progress/?ref=` 를 0.7초마다 조회, 상태 `none/running/complete/failed`).
- **임시 폴더 관리**: `C:\Users\Administrator\zip_cache`(settings `FOLDER_BROWSER_ZIP_CACHE_DIR`). 받는 동안 `.part`, 끝나면 `.zip` 으로 이름을 바꿔 확정한다. **매시 정각에 폴더를 비운다**: 받기를 마친 시각 t 에 대해 `t + 5분` 보다 늦은 첫 정각에 삭제된다(2:00~2:30 에 받은 5개는 3:00 에 모두 삭제, 2:55 이후에 받은 것은 3:00 에는 남고 4:00 에 삭제). 유예 분은 `FOLDER_BROWSER_ZIP_CACHE_GRACE_MINUTES`(5). 서버가 1분마다 확인하는 감시 스레드가 지우므로 요청이 없어도 정각에 비워지며, 읽는 중인 사본은 끝난 뒤에 지운다. 폴더를 외부에서 비워도 안전하다 - 사본이 없으면 다음 요청이 자동으로 다시 받고, 크기가 ECM `fileSize` 와 다른 사본은 버린다. 서버 재시작 뒤에는 남아 있는 정상 사본을 다시 인식해 쓴다(보관 기준은 파일 수정 시각). 용량 상한은 50GB(`FOLDER_BROWSER_ZIP_CACHE_MAX_GB`, 오래된 것부터 삭제, 읽는 중인 사본은 보호)이고, 공간이 부족하면 저장 없이 예전 방식(ECM 에서 직접 흘려받기)으로 동작한다.
- **받기**: ① 파일 클릭/받기 아이콘 = 그 파일 ② zip 행의 받기 아이콘 = zip 파일 자체 ③ 폴더(ECM·zip 안) 행의 아이콘 = 폴더를 zip 으로 ④ 체크박스로 고른 여러 항목 = 하나의 zip(하나만 고르면 그 파일 그대로) ⑤ `현재 폴더 zip 다운로드` ⑥ `전체 zip 다운로드` = 기존 root 전체 zip. 같은 zip 에서 고른 항목은 한 번만 받는다. 항목별 실패는 전체를 멈추지 않고 zip 안 `_다운로드_오류.txt` 에 남고, 열지 못한 항목이 빈 파일로 들어가지 않는다. 암호화된 zip 항목은 표시만 하고 받을 수 없다(잠금 아이콘).
- **API**: `GET /api/projects/<번호>/browse/?ref=&center=&cert_date=`(목록 JSON), `GET /api/projects/<번호>/browse/progress/?ref=`(zip 읽기 진행률), `GET|POST /api/projects/<번호>/browse/download/`(`ref` 1개 GET, 여러 개 POST). 다운로드는 숨은 iframe 으로 호출하고 오류는 `다운로드 오류` 텍스트 첨부로 돌아온다.
- **보안**: 화면에는 ECM OID 를 주지 않고 서버가 서명한 항목 토큰(`ref`, 6시간 만료, 프로젝트 번호에 묶임)만 준다. 목록에서 받은 항목(= 그 프로젝트 root 아래)만 열고 받을 수 있다.
- **이름·정리**: zip 이름은 CP949 를 복원하고, `__MACOSX/`, `._*` 는 숨긴다. 폴더·파일은 자연 정렬(2번 < 10번)이며 폴더가 먼저 나온다.
- **한도(settings)**: `FOLDER_BROWSER_ZIP_MAX_MB`(zip 1개 전송 한도, 기본 1024), `FOLDER_BROWSER_LIST_CACHE_SECONDS`(목록 기억, 900), `FOLDER_BROWSER_MAX_SELECTION`(한 번에 선택, 200), `FOLDER_BROWSER_MAX_FILES`(한 번에 받는 파일 수, 5000), `FOLDER_BROWSER_ZIP_CACHE`(임시 보관 사용, 1), `FOLDER_BROWSER_ZIP_CACHE_DIR`, `FOLDER_BROWSER_ZIP_CACHE_MAX_GB`(50), `FOLDER_BROWSER_ZIP_CACHE_GRACE_MINUTES`(5), `FOLDER_BROWSER_PREFETCH`(1), `FOLDER_BROWSER_PREFETCH_MIN_MB`(30), `FOLDER_BROWSER_PREFETCH_WORKERS`(2).

## 서버 저장소 (재요청 시 ECM 생략)

한 번이라도 요청된 프로젝트의 시험성적서는 서버에 프로젝트번호별 폴더로 보관하고, 같은 프로젝트를 다시 요청하면 ECM 에 접속하지 않고 저장본을 그대로 zip 에 담아 전달한다. 구현 `main/views/review/kolas_report_cache.py`.

```text
C:\Users\Administrator\kolas\          ← settings.KOLAS_REPORT_CACHE_DIR (환경변수 KOLAS_REPORT_CACHE_DIR 로 변경)
  GS-A-25-0077\
    word\GS-A-25-0077 시험성적서.docx
    pdf\GS-A-25-0077 시험성적서.pdf
    _meta.json                         ← 있어야 '완료된 저장본'. 센터·ECM 폴더명·저장시각·파일 크기 기록
```

- 저장 조건: 그 프로젝트의 파일을 **모두 정상으로** 받았을 때만 저장한다. 일부 실패·성적서 없음·폴더 못 찾음은 저장하지 않아 다음 요청에서 ECM 을 다시 시도한다.
- 임시 폴더에 다 쓴 뒤 폴더째 이름을 바꿔 확정하므로 동시 요청·중간 실패로 반쪽 저장본이 남지 않는다.
- 저장본의 파일이 없거나 크기가 `_meta.json` 과 다르면 버리고 ECM 에서 다시 받아 교체한다.
- `_다운로드_결과.txt` 의 성공 줄에 `(서버 저장본)` / `(ECM에서 새로 받음)` 이 표시된다.
- 저장소에 쓸 수 없으면(권한·디스크) 경고 로그만 남기고 다운로드는 그대로 진행한다.
- **갱신 방법**: ECM 에서 성적서가 바뀐(재발급 등) 프로젝트는 그 프로젝트 폴더를 삭제하면 다음 요청에서 최신본을 받는다. API 에는 form 필드 `refresh=1` 도 있다(화면 버튼 없음). 자동 만료는 없다.
- Django 를 실행하는 Windows 계정이 이 폴더에 쓰기 권한이 있어야 한다.
