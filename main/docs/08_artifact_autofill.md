# 산출물 자동 입력 프로그램 설계

## 목적

지금은 download-review 점검 결과(기대값/실제값 불일치)를 작성자에게 전달하면 작성자가 산출물 파일을 열어 수기로 고친다. 이 문서는 그 수기 수정 중 "프로젝트 메타데이터성 값"을 프로그램이 대신 채워 넣는 자동 입력 기능을 설계하기 위한 진행 문서다.

작업은 다음 순서로 진행한다.

1. 현재 최종적으로 생성되는 모든 변수를 정리하고, 변수별로 어떤 파일/구글시트에서 만들어지는지 확인한다. (이 문서의 "변수 사전")
2. 현재 점검하는 파일 목록과, 파일별로 어떤 변수를 사용해 어떤 값을 점검하는지 정리한다. (이 문서의 "파일별 점검 목록과 사용 변수")
3. 변수별로 기대값을 가져오는 곳이 제대로 설정되어 있는지 확인한다.
4. 확인이 끝난 변수부터 실제 자동 입력 로직(템플릿 매칭 → 값 치환)을 구현한다.

점검 규칙 자체의 판정 기준 원문은 `02_inspection_rules.md`가 단일 기준 문서다. 이 문서는 그 내용에서 "변수가 어디서 오고 어디에 쓰이는지"만 뽑아 자동 입력 설계용으로 재구성한 것이다.

## 지금까지 정리된 전제

### 프로젝트 번호는 항상 정확한 값으로 시작한다

`{project_number}`/`{프로젝트번호}`는 자동 입력 실행 전에 다음 중 하나로 확정한다.

- 산출물 폴더 구조/파일명에서 자동 인식.
- 자동 인식이 안 되면 사용자에게 수동 입력을 요청.

이후 모든 공통 변수 조회는 이 확정된 프로젝트번호를 키로 사용한다. 이 값 자체는 비교 기준이지 자동 입력 대상이 아니다.

### 공통 변수는 신규 "GS 정보 확인용" 구글시트에서 가져온다

`main/utils/ecm_reference_sheet.py`(구 인증위 시트)와 `SwData`(인증획득목록 엑셀)는 이번 자동 입력 기능의 기대값 출처에서 제외한다. 대신 `main/utils/google_sheet_reference.py`의 `SOURCES`(센터별 "GS 정보 확인용" 시트, 현재 "상암 시험 진행 현황" 1개만 등록)를 기대값 출처로 쓴다.

### C. 산출물 폴더 파생 변수 (규칙이 실제 제출 파일 내용을 읽어 산출, 후속 규칙에 전달)

| 변수 | 산출 규칙/파일 | 산출 위치 |
| --- | --- | --- |
| `{결함차수}` | 8번 시험성적서, Word | "결함리포트 송부" 표에서 차수별 보고일자 개수 |
| `{1차}`, `{2차}`, `{3차}`, `{4차}` | 8번 시험성적서, Word | 같은 표의 `N차: yyyy.mm.dd` 문구 |
| `{시험성적서_세부사양표}` | 8번 시험성적서, Word | `<세부사양>` 다음 표 전체 |
| `{시험성적서_시험일정}` | 8번 시험성적서, Word | `소요일수` 헤더 표(4.4 시험일정) |
| `{시험성적서_시험기간}` | 8번 시험성적서, Word | `6. 시험기간 :`~`7. 시험방법` 구간의 날짜 목록 |
| `{잔여결함수}` | 10번 결함리포트, 마지막 버전 Excel | `최종결함리포트` 시트 B5 이하 값 있는 셀 수 |
| `{H}` | 10번 결함리포트, 마지막 버전 Excel | `시험분석자료` 시트, 결함정도=`H` 카운트 |
| `{R}` | 10번 결함리포트, 마지막 버전 Excel | `시험분석자료` 시트, `수정전` 값 |
| `{측정항목별점수표}` | 12번 점검표, Excel | `측정항목별 점수표` 시트 D7:D90 |
| `{품질부특성측정값}` | 15번 품질검사표, Excel | E4:E85(33개 값, 27번째 제외, `4~26,28~33,1~3` 재정렬) |

이 변수들은 프로젝트 메타데이터가 아니라 **작성자가 실제로 수행한 시험 결과**이므로, 자동 입력이 "정답을 만들어 채워 넣는" 대상이 아니라 **문서 간 값이 서로 일치하는지 대조하는 참고자료**로만 쓴다(예: 시험성적서에 적힌 결함차수와 실제 결함리포트 파일 개수가 맞는지).

| 구분 | 규칙 | 비고 |
| --- | --- | --- |

## 남은 미해결 항목

| 항목 | 내용 |
| --- | --- |
| `{인증위}` 출처 없음 | 신규 "GS 정보 확인용" 시트에는 인증위 날짜 컬럼이 없다. 한편 `reference_project`에는 전용 `cert_committee_date`(date) 컬럼이 이미 있는데, 이 컬럼은 레거시 `sync_reference_projects_from_sheet`만 채우고 읽는 곳은 프로젝트 목록 정렬뿐이다 — 점검 엔진은 `cert_date`(인증서 발급일과 인증위 개최일이 섞이는 문자열 컬럼)를 읽는다. 선택지는 (1) 신규 시트에 인증위 컬럼 추가, (2) `cert_committee_date`를 신규 시트나 구 인증위 시트로 계속 채우고 엔진이 이 컬럼을 읽게 변경, (3) 이 항목만 수기 유지. 코드 확인 근거는 `04_data_and_api.md`의 `reference_project` 절 참고. |
| 분당/영남 시트 미등록 | `google_sheet_reference.SOURCES`엔 상암만 있다. 두 센터 프로젝트는 아직 이 경로로 공통 변수를 못 채운다. |
| 점검 엔진 미연결 | `google_sheet_reference.lookup_project`는 현재 로컬 앱 "직접 입력" 자동완성 API(`reference_google_sheet_lookup`)에서만 쓰인다. 실제 점검 엔진(`ecm_download_review_inspection.py:_build_rule_context`)은 여전히 `ecm_row_json`/`SwData`를 본다. 자동 입력 기능은 이 조회 경로를 교체하거나 별도 경로를 새로 만들어야 한다. |
| 캐시 TTL | 시트 조회는 5분 캐시(`_CACHE_TTL_SECONDS = 300`)라 시트 수정 직후 값이 곧바로 반영되지 않을 수 있다. |

## 변수별 기대값 출처 점검 체크리스트

자동 입력 로직을 붙이기 전에 변수마다 아래를 확인한다.

- [ ] 값이 신규 "GS 정보 확인용" 시트의 어느 열에서 오는지 명확한가(위 "변수 사전 B" 참고).
- [ ] 해당 프로젝트의 센터에 맞는 시트가 등록되어 있는가(현재 상암만 등록).
- [ ] 점검 엔진이 이 시트를 실제로 조회하는가, 아니면 아직 `ecm_row_json`/`SwData`를 보고 있는가.
- [ ] 값이 비어 있거나 시트에서 프로젝트를 못 찾을 때 자동 입력을 어떻게 처리할지 정했는가(건너뜀/오류/수동 입력 요청).
- [ ] 파생값(변수 사전 C)은 자동 입력 대상에서 제외했는가 — 실제 시험 데이터를 프로그램이 임의로 만들어 넣지 않도록.

## 최종 목표 아키텍처

1. **템플릿 저장**: 규칙별(위 "파일별 점검 목록"에서 공통변수를 쓰는 규칙) 변수가 이미 자리표시자로 작성된 템플릿 산출물 세트를 서버에 저장해 둔다(예: 시험계획서 템플릿의 담당자 칸에 `{담당자}` 자리표시자).
2. **프로젝트 정보 확인**: 자동 입력 실행 시점에 확정된 프로젝트번호로 공통 변수(구글시트)와 고정 상수(config_json)를 모아 "이번 프로젝트의 기대값 집합"을 만든다.
3. **대상 파일 탐색**: 지정한 산출물 폴더에서 `02_inspection_rules.md`의 폴더 탐색/파일명 매칭 규칙과 동일한 방식으로 각 규칙에 해당하는 실제 제출 파일을 찾는다.
4. **값 치환**: 템플릿과 실제 제출 파일의 구조(표 위치, 머리글/바닥글, 표지 셀 등)를 매칭해, "변수 사전 B/D"(공통변수·고정상수)로 분류된 자리에만 기대값을 그대로 써넣는다. "변수 사전 C"(실측 데이터)가 들어가는 자리는 건드리지 않는다.
5. **재검사**: 값을 써넣은 뒤 기존 점검 규칙(1~18번)을 다시 돌려 자동 입력이 실제로 부적합을 해소했는지 확인한다.
